## Summary

- allow Triton matmul kernels to keep the MX-scaled activation path when the rhs is dense FP16/BF16
- mirror the shared-memory sizing estimate for MX lhs x FP16/BF16 rhs
- extend the existing end-to-end matmul grid with BF16-output MXFP8/MXFP4 lhs x BF16/FP16 rhs cases
- cover dense-rhs lhs-scale swizzling and one larger-K split-K path

## Why

The matmul kernels already support microscaled operands through `dot_scaled`, but the current kernel contract assumes microscaled activations only appear alongside microscaled weights. That blocks the valid MXFP8-activation x BF16-weight case and can also underestimate shared-memory pressure for the corresponding launch path.
