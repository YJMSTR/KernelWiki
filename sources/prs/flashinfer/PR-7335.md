## Upstream PR description (verbatim excerpt)

<!-- upstream-excerpt-start -->
`flashinfer.mla.nvfp4_sparse_mla_decode(..., backend="cake")` has a single data-type/layout form. It takes E4M3 queries `[T, 16, 576]` and int32 top-k row ids (`-1` = empty slot) that select 352-byte NVFP4 (`nvfp4_ds_mla`) KV cache rows, and it writes BF16 output `[T, 16, 512]`. This PR replaces the backend's seven `mma.sync` programs (one per cluster size) with 35 tcgen05 programs, each built for sm_100a and sm_103a. They cover 7 cluster sizes (1, 2, 3, 4, 5, 6, 8 CTAs per token) and 5 split bounds (at most 64, 128, 192 or 256 keys per CTA, or any). The host plan considers only the cluster sizes that fit every token's cluster into one wave, and picks the one with the least work per CTA. The baseline is the previous Cake version of `backend="cake"` as shipped on FlashInfer main. Speedup = previous latency / new latency, so > 1 means the new programs are faster. The new programs are faster on every row on both GPUs. On B200 the geomean over 39 rows is 1.131x (range 1.020x to 1.305x). On GB300 the geomean over 40 rows is 1.152x (range 1.028x to 1.375x).

Latency is in microseconds per launch, with the same inputs for both sides and 16 heads. P rows: T = 5..45 tokens per launch at top
