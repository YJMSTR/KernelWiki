## 📌 Description

Thread the explicit NVFP4 4over6 recipe (#5152's `nvfp4_4over6=` / `QuantConfig.nvfp4_4over6`) into the TRT-LLM gen and CUTLASS fused MoEs, whose in-kernel NVFP4 activation quantizations still resolved the recipe from `FLASHINFER_NVFP4_4OVER6*` only; expose it on the public CuteDSL entry points, which #5152 had left without it; and record it in the FP4 MoE trace definitions. One commit per part.

TRT-LLM gen:

- `MoERunnerArgs.nvfp4_4over6_code` (wire code of `resolveNVFP4Recipe()`, -1 = environment); trailing FFI argument of `trtllm_fp4_block_scale_moe`; `trtllm_fused_moe_runner.cu` decodes it instead of `kNVFP44Over6FromEnv`.
- Flat `trtllm_fp4_block_scale_{,routed_}moe` take `nvfp4_4over6=` (unset = environment, `None` = off, `NVFP44Over6Config` = that recipe; the last is what "pinned recipe" means below and in #5152's docs). A pinned recipe is rejected before any device work unless the call is on the per-token NVFP4 path (`per_token_scale` with uint8 `hidden_states`): the standard path's GEMM1 epilogue and the MXFP8 per-token path have no 4over6 variant.
- `TrtllmFp4RoutedRunner` opts in with CuteDSL's per-token-only
