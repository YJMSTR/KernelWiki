## Motivation

Kimi-K3's merged MoE front projection (`(N, K) = (6016, 7168)`, FP32 output so the router logits keep their precision) runs through TGV at the spec-verify batch sizes. On SM107 a warp split-K design with cp.async ring loads is faster at `M = 8, 16, 32`.

- `dense_bf16_gemm_warp_splitk.py` (new, **temporary copy**): FlashInfer already ships this kernel as `flashinfer/gemm/kernels/dense_bf16_gemm_warp_splitk.py` (`run_warp_splitk_dense`, also behind `flashinfer.gemm.bf16_gemm_sm100` with the cute-dsl runners), but its input validation only accepts a bf16 `out`, in 0.7.2.post1 and on main. K3's merged front projection needs FP32 output to keep router-logit precision, so this copy differs from FlashInfer's file by 71 lines, essentially `out.dtype in (bf16, fp32)` and keying the compile cache on the output dtype.
