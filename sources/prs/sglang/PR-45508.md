## Motivation

This PR is powered by [KDA](https://github.com/NVlabs/kda) team. `MuseSpark1xRouter` computes FP32 router logits on a side stream in every MoE layer, and the MoE waits for it. At one decode token cuBLAS runs this as a split-K GEMV plus a separate reduce kernel. In NVFP4 batch-1 decode on GB300 the main stream waits 146-152 us per step (of about 5.4 ms) for the router.

## Modifications

- `kernels/ops/gemm/muse_spark_router_gemv_cutedsl.py` (new): a CuTe DSL FP32 GEMV with one launch, no split-K workspace and a fixed reduction order, so results are deterministic and differ from cuBLAS only by FP32 summation order
- `router_gemv_cute_eligible` admits FP32 inputs on SM10x GPUs with aligned rows. Muse Spark enables TF32, under which cuBLAS already runs multi-row logits as a TF32 GEMM, so only the one-token decode call moves
- `srt/models/muse_spark.py`: `MuseSpark1xRouter.forward` calls the kernel when eligible and keeps `F.linear` otherwise
- `kernels/ops/gemm/__init__.py`, `test_kernels_namespace.py`: register `gemm.muse_spark_router_gemv` in the kernel inventory
- `test_muse_spark_router_gemv_cutedsl.py` (new): FP64 reference with an FP32 error bound, 1-16 tokens, mi
