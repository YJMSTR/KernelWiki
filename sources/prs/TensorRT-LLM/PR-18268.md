## Description

The DSA (sparse attention) backend rebuilds its per-step decode metadata in
`DSAtrtllmAttentionMetadata.on_update_kv_lens` as a chain of ~30 small eager
pointwise/scan launches: the token→request map (`req_idx_per_token`), the
fp8/scale indexer-cache slot mappings, and the two int64 generation `indptr`
cumsums. At decode the batch is tiny, so this chain is dominated by kernel
launch / host overhead on the critical path.

This PR adds a single Triton kernel (`fused_metadata.py`) that produces the same
five integer metadata tensors in one launch:

- a header program computes the two int64 `indptr` cumsums;
- one program per request writes `req_idx_per_token` and the fp8/scale slot mappings.

The outputs are **bit-identical** to the eager chain (a wrong index would
silently corrupt sparse attention).

### Scope / safety

- **Opt-in** via `TRTLLM_FUSED_DSA_METADATA=1`; the default keeps the existing eager path.
- Engages **only** on the pure-decode/generation step (`num_contexts == 0`).
  Context/prefill, mixed batches, and the `fp8_ds_mla` cache mode (which additionally
  needs `token_positions_cuda`) fall back to the eager chain.
