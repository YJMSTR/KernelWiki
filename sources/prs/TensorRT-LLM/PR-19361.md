## Summary

Text-only follow-up to the SM107 (Rubin) bring-up. Docs, developer guides, code comments and error strings still said "SM100/SM103" for paths whose actual gates (`is_sm_100f` = `100 <= sm < 110`, `isSM100Family()`, trtllm-gen `ARCHS 100 103 107 100f`, `_MLA_*_SUPPORTED_SM_VERSIONS`) already accept SM107. Every changed line was traced to its gate and, for TRTLLM-Gen MoE, to the exported cubin table.

Main edits:
- **One code fix (review finding):** `TrtllmTrtllmGenW4a8Nvfp4Fp8Impl.can_implement` now rejects SM107 (`SM_UNSUPPORTED`). The batchedGemm export ships E2m1-weight x E4m3-activation kernels only as `sm_100a`/`sm_103a` cubins (no `sm_100f`/`sm_107a`), so the family-wide `is_sm_100f` gate let SM107 through to a "No kernel found" at runner construction. Unit test added in `test_moe_impl.py`.
- `MOE_DEVELOPER_GUIDE.md`: TRTLLMGen / DeepGemm / MegaMoE-DeepGemm cells and backend table add SM107. Cutlass and DenseGEMM cells unchanged (their Python gates exclude SM107).
- `docs/source/features/quantization.md`: `Rubin(sm107)` row (Y everywhere except NVFP4 KV cache, which is forced to FP8 on SM107).
