## Problem

fp8 `T.gemm` picks the `m16n8k32` fp8 MMA atom from the dtype alone. On `sm_80`/`sm_86`, which have no `.e4m3`/`.e5m2` `mma.sync`, the CUTLASS atom compiles to `CUTE_INVALID_CONTROL_PATH`, so nvcc succeeds and the kernel traps at launch with `device-side assert triggered`.

## Fix

Reject fp8 operands on the `mma.sync` path below SM89 in `cuda::Gemm::SelectInst`, next to the existing Volta/Turing gates, with a message naming the dtypes and target. WGMMA/TCGEN05 return earlier and Volta/Turing already fall back to FMA, so only `sm_80`–`sm_88` is affected.

## Tests

New `testing/python/kernel/test_tilelang_kernel_fp8_gemm_arch_gate.py` (compile-only, explicit targets, `requires_cuda`):

- `sm_80`/`sm_86` × `e4m3fn`/`e5m2` are rejected.
- `sm_89` fp8 and `sm_80` fp16 still lower to `tl::mma_sync`.
